# День 12 — Персонализация ассистента

## Проблема

После Day 11 у агента есть три слоя памяти (short-term / working / long-term), но нет
**персонализации**: агент не знает, *кому* он отвечает и *как* этот человек хочет получать
ответы. Long-term память — это факты, которые агент **сам вывел** из диалога ("травма плеча",
"цель — полумарафон"). Профиль — это то, что пользователь **сам заявил** о себе и о том, как с
ним работать (тон, формат, ограничения) — и он должен применяться на *каждом* запросе, а не
только когда что-то напомнило о нём.

## Модель профиля (`agent/profile/UserProfile.kt`)

Один глобальный, редактируемый профиль — **не** каталог из нескольких профилей и **не**
переключатель. В этом смысле он устроен так же, как long-term память Day 11 (`agent/memory/LongTermMemoryStore`):
один файл, одно значение на всё приложение.

| Поле | Смысл | Пример |
|------|-------|--------|
| `displayName` | как обращаться | «Аня» |
| `about` | контекст о пользователе | «тренируется дома, без инвентаря» |
| `language` | язык ответа | «русский» |
| `expertise` | уровень (`BEGINNER`/`INTERMEDIATE`/`ADVANCED`) | `BEGINNER` |
| `tone` | стиль общения | «дружелюбно, поддерживающе» |
| `format` | формат ответа | «короткий список шагов» |
| `maxAnswerSentences` | ограничение длины (**инструкция**, не жёсткая обрезка) | 5 |
| `constraints` | жёсткие ограничения, список | «нет доступа к залу», «травма колена» |
| `notes` | прочие пожелания | «не любит кардио» |

`UserProfile.EMPTY` — профиль без единого установленного поля: `ProfileRenderer.render` для
него возвращает пустую строку, и агент ведёт себя ровно как до Day 12. При первом запуске
`UserProfileStore.load()` возвращает не `EMPTY`, а `UserProfile.STARTER` — заполненный
пример-«рыбу», который пользователь правит под себя, вместо пустой формы.

## Профиль vs long-term память — граница

|                     | Long-term память (Day 11)                  | Профиль (Day 12)                              |
|---------------------|---------------------------------------------|------------------------------------------------|
| Что это             | Факты, которые агент **узнал**              | Предпочтения, которые пользователь **заявил**   |
| Кто пишет           | `MemoryRouter` (LLM) + ручной "Promote"/"Add" | Пользователь (UI) + подтверждённое предложение `PreferenceAdvisor` |
| Формат              | Произвольные `key: value` факты             | Фиксированная структура (`UserProfile`)         |
| Место в промпте     | Тело промпта, рядом с working memory        | System instruction агента                       |
| Сколько штук        | Одна (на приложение)                        | Одна (на приложение)                            |

`MemoryRouter` в профиль никогда не пишет, `PreferenceAdvisor` никогда не пишет в память — это
два независимых механизма, с отдельным учётом токенов
(`memoryRoutingTokensTotal` vs `personalizationTokensTotal`).

## Как профиль попадает в запрос (`agent/LlmAgent.kt`)

`ProfileRenderer.render(profile)` детерминированно (без LLM) рендерит профиль в один блок
«User profile (personalization directives — follow these when answering): …». `LlmAgent.handle`
получает этот блок через `AgentRequest.userProfile` и склеивает его с персоной агента:

```
effectiveSystemInstruction = config.systemInstruction + "\n\n" + profileBlock
```

Ключевое архитектурное решение: блок уходит в **system instruction**, а не в тело
пользовательского сообщения (где живут `longTermMemory`/`workingMemory`/`history`, см. Day 11).
Причина — это инструкция «как отвечать», а не факт из разговора; system instruction обычно
имеет больший вес при следовании модели инструкциям, и хранится отдельно от растущего диалога.

`ChatViewModel.prepareRequestContext` рендерит и передаёт профиль **на каждом ходу**, без
участия пользователя — это и есть проверка «ассистент учитывает автоматически» (см. также
`PersonalizationTest`, где показано, что один и тот же вызов `agent.handle` с разными профилями
даёт разные `systemInstruction`, при неизменном `input`).

Стоимость профиля учитывается в токенах наравне с остальными частями промпта:
`TokenUsage.profileTokens` входит в `promptTokens`, а значит — и в проверку контекстного окна
из Day 8 (`ContextWindowExceededException`).

## Гибридное обновление профиля

Профиль можно редактировать вручную в UI (`ProfilePanel`), но он не автообновляется молча:

1. После каждого хода `PreferenceAdvisor` (отдельный LLM-вызов, `agent/profile/PreferenceAdvisor.kt`)
   проверяет, не заявил ли пользователь только что предпочтение («отвечай короче», «без штанги»,
   «обращайся ко мне Марк»).
2. Если да — возвращает JSON `{"field", "value", "reason"}` (или литерал `null`, если ничего не
   заявлено). Парсинг устойчив к мусору/markdown-обрамлению/незнакомому полю — в этих случаях
   просто ничего не предлагается, диалог не ломается.
3. Предложение показывается баннером в `ChatScreen` с кнопками **Применить**/**Отклонить**
   (`ChatViewModel.onApplySuggestion`/`onDismissSuggestion`). Профиль меняется **только** после
   явного подтверждения — ни разу автоматически.

Специальные псевдо-поля `add_constraint`/`remove_constraint` позволяют предлагать изменения
множества `constraints` (это список, а не одиночное значение, как остальные поля).

## Проверка результата

- **Ответы для разных профилей**: `PersonalizationTest` — один и тот же вопрос через один и тот
  же `LlmAgent.handle` под двумя разными наполнениями профиля («новичок дома, без инвентаря» vs
  «продвинутый, травма колена») даёт два разных `systemInstruction` (ограничения и стиль каждого
  видны только в своём промпте), при полностью одинаковом `input`. Ручной сценарий с реальным
  ответом — `docs/day12-personalization-test-scenario.md`.
- **Учитывается автоматически**: пользователь не повторяет предпочтения в сообщении — профиль
  подмешивается в system instruction на каждом вызове `prepareRequestContext`, что подтверждено
  тестом (`the profile is applied automatically without the caller repeating anything in the
  message`) и видно в UI как `profile N` в разбивке токенов ответа.
- **Пустой профиль = поведение до Day 12**: отдельный тест сравнивает промпт без `userProfile` и
  с `ProfileRenderer.render(UserProfile.EMPTY)` — они идентичны.

## Ограничения и заметки

- Профиль и long-term память — оба глобальные, оба одиночные; переключение ветки диалога (Day 10)
  не влияет ни на один из них. Это осознанный компромисс, а не забытая интеграция: привязка
  long-term памяти к профилю — очевидная точка расширения, если в приложении появится
  многопользовательский режим.
- `maxAnswerSentences` — это инструкция для модели ("держись примерно в N предложений"), а не
  программная обрезка ответа; модель может её не соблюсти в точности.
- `PreferenceAdvisor` — дополнительный LLM-вызов на каждый ход пользователя; его стоимость
  видна отдельно (`personalizationTokensTotal`), чтобы не путать с ценой самого диалога
  (`dialogTokenTotal`) или роутера памяти (`memoryRoutingTokensTotal`).
