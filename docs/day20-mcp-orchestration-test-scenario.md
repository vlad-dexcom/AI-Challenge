# Сценарий проверки оркестрации MCP-серверов (Day 20)

Ручной сквозной сценарий для проверки, что персона **«Orchestrator Coach (multi-server MCP)»**
сама выбирает нужный сервер/инструмент под запрос и умеет прогонять флоу, пересекающий несколько
MCP-серверов, за один ход.

---

## Подготовка

1. Убедитесь, что в `local.properties` задан рабочий `GEMINI_API_KEY`.
2. Соберите и установите отладочную сборку:
   ```bash
   ./gradlew :app:installDebug
   ```
3. Откройте приложение — попадаете в обычный экран чата.

---

## Шаг 1 — Выбор персоны

В выборе агента/персоны выберите **«Orchestrator Coach (multi-server MCP)»**.

---

## Шаг 2 — Запрос, пересекающий все три сервера

Напишите агенту:

```
Проверь Squat по внешней базе, составь и сохрани тренировку на ноги на 30 минут под названием
"Leg Day", и залогируй её как выполненную.
```

```
Хочу тренировку на грудь дома с гантелями на 40 минут. Проверь упражнения по внешней базе и,
 если план ок, сохрани его и отметь как выполненную сегодня
```

**Ожидаемый результат:** за один ответ агент автоматически вызывает 5 инструментов подряд, на
трёх разных серверах:

1. `get_exercise_info(name="Squat")` — **удалённый** сервер (wger).
2. `find_exercises(goal="legs", level="intermediate")` — **локальный** `workout-planner`.
3. `build_workout_plan(exercises_json=<результат шага 2>, goal="legs", level="intermediate",
   minutes=30)` — тот же `workout-planner`.
4. `save_workout_plan(name="Leg Day", plan_json=<результат шага 3>)` — тот же `workout-planner`.
5. `log_workout(goal="legs", minutes=30)` — **другой** локальный сервер, `workout-digest`.

Откройте экран **MCP** («Call log») — должны появиться все 5 вызовов подряд, в этом порядке, с
итогом `ok` у каждого. Финальный ответ агента должен подтвердить: упражнение проверено, план
сохранён под именем "Leg Day", тренировка залогирована.

---

## Шаг 3 — Проверка правильной маршрутизации (а не просто порядка)

Это ключевая проверка Day 20 — не просто "5 вызовов подряд", а "каждый вызов ушёл на верный
сервер":

- В логе `callTool(get_exercise_info, ...)` должен идти **после** `connect(...)`/`listTools()`,
  вызванных для удалённого сервера wger (а не для локальных).
- `callTool(save_workout_plan, ...)` и `callTool(log_workout, ...)` — оба "про тренировки", но
  должны попасть на **разные** гейтвеи (`workout-planner` и `workout-digest` соответственно). Если
  агент перепутал их (например, вызвал `save_workout_plan` вместо `log_workout` или наоборот) —
  это баг маршрутизации, который и призван ловить этот сценарий.

---

## Шаг 4 — Деградация при недоступном удалённом сервере

1. Отключите сеть на устройстве/эмуляторе (или временно испортите `McpConfig.FITNESS_SERVER_URL`).
2. Повторите запрос из Шага 2.

**Ожидаемый результат:** `get_exercise_info` завершается ошибкой соединения, но агент **не
падает целиком** — он кратко сообщает, что не смог проверить упражнение по внешней базе, и всё
равно продолжает: строит и сохраняет план, логирует тренировку (шаги 2–5 по-прежнему проходят
через локальные серверы). В логе `callTool` для `wger` не появится вовсе (соединение не
установлено), но записи для `workout-planner`/`workout-digest` — появятся.

---

## Шаг 5 — Запрос только к одному серверу (без оркестрации по всем трём)

```
Какие упражнения предлагаются для спины с гантелями?
```

**Ожидаемый результат:** агент вызывает только `suggest_workout` (удалённый сервер) — не трогает
ни `workout-planner`, ни `workout-digest`, поскольку просьбы построить/сохранить план или
залогировать тренировку не было.
