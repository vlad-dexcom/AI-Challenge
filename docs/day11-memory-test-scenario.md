# Сценарий проверки модели памяти (все три слоя)

Ручной сквозной сценарий для агента **Personal Trainer** (`personal-trainer`). Цель — на одном
диалоге явно показать, что именно попадает в **short-term** / **working** / **long-term** и как
это меняет ответы агента. После каждого хода — что проверять в `MemoryPanel` (кнопка "Show") и
чего ожидать от ответа. Нумерация ходов сквозная.

Предполагается чистое состояние: новый чат (или "Clear dialog" + пустые working/long-term —
можно удалить `chat_history.json` / `working_memory.json` / `long_term_memory.json` вручную
перед стартом, если нужно гарантированно начать с нуля).

## Часть 1 — наполнение long-term (профиль)

**Ход 1.**
Пользователь: `Мне 34 года, у меня травма плеча — нельзя жим над головой.`

Проверить в `MemoryPanel` → **Long-term**: должны появиться примерно `age: 34` и
`injury_shoulder: cannot do overhead press` (формулировка ключей у роутера может отличаться —
важен факт, а не точное имя ключа). В **Working** на этом шаге пока пусто.

**Ход 2.**
Пользователь: `Ещё я вегетарианец, если это важно для восстановления после тренировок.`

Проверить: в **Long-term** добавился ещё один пункт (`diet: vegetarian` или похожий) — это тоже
устойчивый профиль, не задача.

## Часть 2 — наполнение working (текущая задача)

**Ход 3.**
Пользователь: `Составь план тренировок на 4 недели, начнём с кардио.`

Проверить в **Working**: должны появиться `task`/`goal` (что-то про "4-week plan") и, возможно,
`week: 1`. Long-term не должен измениться — задача не про пользователя, а про текущую цель.

**Ход 4.**
Пользователь: `Хорошо, план понятен. Какая должна быть длительность кардио в первую неделю?`

Ответ агента должен опираться на **working** (детали текущего плана), не переспрашивая заново
"какой у вас план" — working-факт с хода 3 должен быть виден модели.

## Часть 3 — recall-проверка (эффект long-term при "устаревшей" истории)

**Ходы 5–12.** Заполните диалог нейтральными вопросами, не касающимися плеча/диеты, чтобы
раздвинуть историю за пределы `MemoryRouter.RECENT_CONTEXT_SIZE` (8 сообщений). Например:
- `Что съесть перед тренировкой?`
- `Сколько отдыхать между подходами?`
- `Как правильно делать выпады?`
- `Нужна ли растяжка после кардио?`
- (продолжайте, пока не наберётся ~8 сообщений истории после хода 1)

**Ход 13 (ключевая проверка).**
Пользователь: `Можно ли мне добавить жим лёжа на этой неделе?`

Ожидаемый эффект: несмотря на то что сам ход 1 (про травму плеча) уже физически выпал из
последних `RECENT_CONTEXT_SIZE` сообщений истории, агент **всё равно** должен предупредить про
травму плеча / скорректировать рекомендацию — потому что `injury_shoulder` хранится в long-term
и рендерится в промпт независимо от длины истории (см. `LlmAgentTest`:
`long-term memory keeps an old fact in the prompt after it has fallen out of recent history`).

Если убрать long-term (гипотетически) — агент бы не знал о травме, т.к. её больше нет в окне
истории (см. второй тест: `without long-term memory an old fact ... never reaches the prompt`).
Это и есть измеримое влияние слоя памяти на ответ.

## Часть 4 — короткосрочная память и "Clear dialog"

**Ход 14.**
Нажать **"Clear dialog"**.

Проверить: сообщения диалога (short-term, `chat_history.json`) очищены. При этом открыть
`MemoryPanel` — **Working** и **Long-term** должны остаться нетронутыми (план тренировок и
профиль с травмой/диетой всё ещё там).

**Ход 15.**
Пользователь (в новом, пустом диалоге): `Что там с моим планом на этой неделе?`

Ожидаемый эффект: агент отвечает по существу, опираясь на **working** (план всё ещё в
`working_memory.json`), хотя весь текст предыдущего диалога стёрт — это доказывает, что working
не хранится "внутри" истории сообщений, а отдельно.

## Часть 5 — "End task" (working memory)

**Ход 16.**
Нажать **"End task"**.

Проверить: **Working** для текущей ветки очищена (плана/недели больше нет). **Long-term**
(травма, диета) остался как есть — кнопка чистит только один слой.

**Ход 17.**
Пользователь: `Составь мне новый план — только на этот раз силовой.`

Ожидаемый эффект: агент по-прежнему учитывает травму плеча (long-term пережил "End task"), но не
пытается опираться на старый 4-недельный кардио-план (working-факт удалён) — новая задача
стартует "с чистого листа" по задаче, но не по профилю.

## Часть 6 — ручные overrides (`MemoryPanel`)

**Шаг 18a — Promote.**
В `MemoryPanel` найти рабочий пункт (например `task: strength plan`) и нажать **Promote**.

Проверить: пункт исчез из **Working** и появился в **Long-term** с тем же значением, помечен
как закреплённый (`pinned`). Это ручное решение "какая информация должна пережить задачу".

**Шаг 18b — Add (вручную в long-term).**
В `MemoryPanel` добавить вручную пару, например ключ `preferred_time`, значение `evening`.

**Ход 19.**
Пользователь: `Когда мне лучше тренироваться?`

Ожидаемый эффект: агент использует `preferred_time: evening`, хотя пользователь никогда явно не
говорил этого в диалоге в текущей сессии — значение попало только через ручной ввод в UI, что
доказывает: memory-panel влияет на промпт так же, как автоматический роутер.

**Шаг 18c — Delete.**
Удалить в `MemoryPanel` пункт про диету (`diet: vegetarian`) из **Long-term**.

**Ход 20.**
Пользователь: `Что съесть на ужин после тренировки?`

Ожидаемый эффект: агент больше не учитывает вегетарианство (совет может включать мясо/рыбу) —
подтверждает, что удаление конкретного пункта немедленно влияет на следующий ответ и не требует
перезапуска.

**Шаг 18d — попытка роутера переписать pinned-пункт.**
После шага 18a (`task` теперь `pinned` в long-term) отправьте ещё один ход, из которого роутер
мог бы захотеть само собой изменить/удалить этот пункт (например, обсуждение совсем другой темы,
никак не связанной с планом). Проверить: значение `task` в **Long-term** осталось прежним и
`pinned = true` — guard rules не дали роутеру перезаписать ручной ввод (см. `MemoryRouterTest`).

## Что фиксирует каждый ход (сводная таблица)

| Ход | Слой, который проверяем | Что должно произойти |
|-----|--------------------------|------------------------|
| 1–2 | Long-term | Устойчивые факты профиля появляются, working пуст |
| 3–4 | Working | Данные текущей задачи появляются, отвечают на уточняющий вопрос |
| 5–12 | Short-term (окно) | История растёт за пределы `RECENT_CONTEXT_SIZE` |
| 13 | Long-term vs. short-term | Long-term факт всё ещё влияет на ответ, хотя выпал из окна истории |
| 14–15 | Short-term isolation | "Clear dialog" не трогает working/long-term |
| 16–17 | Working isolation | "End task" не трогает long-term |
| 18a–18d | Ручные overrides | Promote/Add/Delete меняют слой сразу же; pinned защищён от роутера |

## Автоматические аналоги этого сценария

Ручной прогон выше воспроизводит (на уровне UI и живой модели) то, что уже проверено юнит-тестами
без сети:
- изоляция слоёв/веток и round-trip персистентности — `MemoryLayersTest.kt`;
- guard rules (pinned переживает роутер, лимиты, нормализация) — `MemoryRouterTest.kt`;
- влияние long-term памяти на итоговый промпт при "устаревшей" истории (часть 3 выше) —
  `LlmAgentTest.kt`, тесты `long-term memory keeps an old fact in the prompt after it has fallen
  out of recent history` и `without long-term memory an old fact absent from recent history
  never reaches the prompt`.

Ручной прогон нужен там, где автоматика невозможна без реального LLM: качество *классификации*
роутера (правильно ли конкретный факт ушёл в long-term, а не working) — см. раздел "Качество
ответов живого LLM-роутера" в `docs/day11-memory-model.md`.
