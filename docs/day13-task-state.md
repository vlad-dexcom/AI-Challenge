# День 13 — Состояние задачи как конечный автомат (Task State Machine)

## Проблема

К Day 12 у агента есть три слоя памяти (short-term / working / long-term, Day 11) и профиль
(Day 12), но нет формального ответа на вопрос **«на каком этапе задача сейчас и чей ход»**. Эта
информация раньше существовала только неявно — размазана по транскрипту диалога — и агенту
приходилось каждый раз выводить её заново из текста. На практике это приводило к:

- повторному пересказу плана после паузы или перезапуска приложения;
- «убеганию» агента вперёд, пока пользователь ещё не сделал ожидаемое действие;
- потере прогресса при сжатии истории (Day 9) или обрезке скользящим окном (Day 10), потому что
  прогресс жил в самом тексте, который и обрезался.

Day 13 делает позицию задачи **структурированными данными**: конечный автомат с явными этапами,
текущим шагом и ожидаемым действием, персистентный по веткам, рендерящийся в промпт
детерминированно (без LLM) на каждом запросе.

## Модель (`agent/task/TaskState.kt`)

```
PLANNING --> EXECUTION   (approvePlan)
PLANNING --> DONE        (complete — задача отменена до выполнения)
EXECUTION --> VALIDATION (requestValidation)
VALIDATION --> EXECUTION (sendBackToExecution — нужна доработка)
VALIDATION --> DONE      (complete)
```

| Поле | Смысл |
|------|-------|
| `title` | короткое название задачи |
| `stage` | `PLANNING` / `EXECUTION` / `VALIDATION` / `DONE` |
| `steps` | шаги плана, фиксируются при утверждении плана |
| `currentStepIndex` | индекс текущего шага (`-1`, если шагов ещё нет) |
| `expectedAction` / `expectedActor` | что ожидается дальше и чей ход (`USER`/`AGENT`) |
| `paused` | пауза **поверх** текущего этапа, а не отдельный этап |
| `updatedAt` | момент последнего изменения |

`TaskState.NONE` — задача не начата; `TaskStateRenderer.render`/`stageRules` для неё возвращают
пустую строку, и агент ведёт себя ровно как до Day 13 (тот же приём, что `UserProfile.EMPTY` в
Day 12).

**Почему пауза — флаг, а не пятый этап.** Если сделать `PAUSED` отдельным `TaskStage`, теряется
информация «куда возвращаться» и пришлось бы хранить `previousStage` отдельно — то есть тот же
флаг, только сложнее. `pause`/`resume` в `TaskStateMachine` идемпотентны и возвращают ровно то же
состояние (кроме `updatedAt`), что и есть требование «продолжение без повторных объяснений».

## Task state vs working memory (Day 11) — граница

|                 | Working memory (Day 11)   | Task state (Day 13)              |
|-----------------|----------------------------|-----------------------------------|
| Отвечает на     | *что* мы знаем о задаче    | *где* мы в задаче                 |
| Формат          | свободные `key: value`     | фиксированная структура + автомат |
| Кто пишет       | `MemoryRouter` (LLM)       | `TaskStateMachine` (код) / UI     |
| Очистка         | «End task»                 | «End task» (обнуляет и то, и то)  |

## Конечный автомат (`agent/task/TaskStateMachine.kt`)

Единственный код, которому разрешено менять `TaskState` — ни агент, ни UI не мутируют его
напрямую. Каждая операция возвращает `TransitionResult`: `Applied(newState)` или
`Rejected(reason)` — невалидный переход не бросает исключение и не проходит молча, а объясняется
(`"Cannot approve the plan from stage EXECUTION (requires PLANNING)."`), так что UI может
показать причину в `errorMessage`.

Инварианты:
- из `DONE` не выходит ни один переход, кроме `reset()`;
- пока `paused = true`, разрешены только `resume()` и `reset()` — задача заморожена целиком;
- `currentStepIndex` всегда в пределах `steps`, `nextStep`/`previousStep` не выходят за границы;
- `pause()` идемпотентен; `resume()` на не-приостановленной задаче — no-op-переход, а не ошибка.

## Рендер в промпт (`agent/task/TaskStateRenderer.kt`) и проводка в агента

Два раздельных, детерминированных рендера:

- **`render(state)`** — блок *контекста* («Stage: EXECUTION (2 of 4)», «Current step: …»,
  «Expected next action: USER — …», «Status: PAUSED …»). Идёт в тело промпта сразу после working
  memory (`AgentRequest.taskState`), т.к. это контекст задачи, меняющийся от хода к ходу — не
  директива стиля.
- **`stageRules(state)`** — короткое поведенческое правило под текущий этап
  (`AgentRequest.taskStageRules`), приклеивается к system instruction агента (`LlmAgent.handle`),
  как и профиль Day 12: `PLANNING` запрещает выполнение шагов, `EXECUTION` запрещает пересказ
  плана, `VALIDATION` запрещает добавлять новую работу, `paused` полностью останавливает
  продвижение задачи.

`TokenUsage.taskStateTokens`/`taskStageRulesTokens` считаются отдельно и входят в `promptTokens`
(Day 8 бюджет контекста), как и остальные слои.

## Персист по веткам (`agent/task/TaskStateStore.kt`)

Смоделирован буквально по образцу `WorkingMemoryStore`: один файл `task_state.json`, мапа
`branchId -> TaskState`. Переключение веток (Day 10) меняет и панель, и блок в промпте — задача
на ветке «10 км» не путается с задачей на ветке «силовая». Форк ветки из чекпойнта переносит и
задачу — как working memory, но отдельным ключом-«снимком» на чекпойнт.

## Опциональный advisor (`agent/task/TaskStateAdvisor.kt`)

По образцу `PreferenceAdvisor` (Day 12): после хода пользователя, который похож на выполнение
ожидаемого действия («готово», «план утверждён», «не сработало, нужно переделать»), отдельный
LLM-вызов *предлагает* переход (`TaskTransitionSuggestion`). Пользователь подтверждает кнопкой
**Apply** в баннере — предложение никогда не применяется автоматически, и любой одобренный
переход всё равно проходит через `TaskStateMachine`, так что устаревшее предложение (задача уже
сдвинулась) корректно отклоняется. Стоимость считается отдельно
(`ChatUiState.taskStateAdvisorTokensTotal`), не смешиваясь с `MemoryRouter`/`PreferenceAdvisor`.

## UI

Панель «Task» в топбаре чата (см. `ChatScreen.kt`'s `TaskPanel`): сводка «Task: … · STAGE (i of
n) · PAUSED», список шагов с отметкой текущего, строка «Expected: …» и кнопки, зависящие от
этапа/паузы — так что предлагаются только переходы, реально разрешённые `TaskStateMachine`
(нет отдельной кнопки «Next» на `VALIDATION`, например).
