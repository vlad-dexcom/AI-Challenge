# День 25 (неделя RAG): мини-чат с RAG и памятью задачи

Мини-чат поверх конвейера Days 21–24: хранит историю диалога, на каждый вопрос ищет контекст в базе знаний, отвечает по найденному и **всегда** показывает источники
(с проверенными цитатами). Усиление — **task memory** (память задачи): цель диалога, уточнения пользователя и зафиксированные ограничения.
Код: пакет `com.example.rag.chat` в модуле `:rag` (чистая JVM, без зависимости от `:app`). Веб-интерфейс — существующая вкладка **Chat**; есть CLI `chat`.

## Архитектура

| Класс | Роль |
|---|---|
| `ChatSession`, `SessionStore` | сессия (сообщения, память, сводка, трасса каждого хода) в JSON-файле `rag/sessions/<id>.json` (в `.gitignore`), атомарная запись, id проверяется регулярным выражением |
| `TaskMemory` | `goal`, `clarifications[]`, `constraints{}`, `terms{}`, `openQuestions[]`, журнал `changes[]`; все правила слияния — в коде (`merge`, `applyEdit`) |
| `MemoryExtractor` | LLM с JSON-выводом предлагает `MemoryPatch`; строгая валидация типов, при сбое память **не меняется** |
| `ContextualRewriter` | строит самостоятельный поисковый запрос из вопроса + памяти + сводки + последних реплик (на сбое: вопрос + цель/ограничения) |
| `HistoryBudget`, `Summarizer` | последние N ходов дословно + скользящая сводка более старых (при сбое LLM — детерминированная выжимка) |
| `ChatEngine` | один ход диалога (ниже); результат атомарный: при ошибке сессия не меняется, сообщение можно отправить повторно |
| `SessionApi` | HTTP: `GET/POST /api/sessions`, `GET/DELETE /api/sessions/{id}`, `POST …/messages`, `PUT …/memory`, `POST …/memory/reset`, `POST …/reset` |
| `ScenarioRunner`, `ScenarioChecks`, `GoalJudge` | прогон сценариев и проверки (см. ниже) |

Для конвейера добавлены обратно совместимые хуки: `RagPipeline.ask(..., dialogContext)`, `CitedAnswerer.answer(..., dialogContext)` и `DIALOG_RULES` в промпте
(память описывает пользователя и **не является источником**: цитировать можно только фрагменты базы). Приложение `:app` (`Knowledge Coach (RAG)`) работает без изменений.

**Почему отдельный `TaskMemory`, а не классы `:app`.** Концептуально он повторяет память и состояние задачи Days 11–15 (краткосрочная/рабочая/долговременная память, стадии задачи),
но живёт в `:rag`: простой, тестируется без Android и сети. Android-зеркало не делалось (stretch, не требовалось).

## Ход диалога (`ChatEngine.send`)

1. **Извлечение памяти** (LLM, JSON, `temperature=0`) → валидация → слияние. Сбой/невалидный JSON → память без изменений, причина в `memoryNotes`.
2. **Контекстное переписывание запроса** («а для моего колена?» → «knee-friendly squat alternatives beginner»; русский вопрос переводится на английский корпус).
3. Поиск `topKBefore` → фильтр по порогу косинуса (0.65) → rerank → `topKAfter` (4).
4. **Ответ** по контракту Day 24 (ответ, источники, цитаты, проверка кодом) с блоком диалога: память (никогда не обрезается) + сводка + последние N ходов.
5. **«Не знаю»** (ниже порога / модель считает, что ответа нет / проверка не прошла): ответ на языке пользователя, ближайшие темы («не ответ»), уточняющий вопрос и строка «цель остаётся прежней: …»;
   вопрос попадает в `openQuestions`.
6. Окно сдвигается; когда набралась пачка вытесненных ходов (`summaryBatch`), они сворачиваются в сводку.

### Правила памяти
- Цель задаётся, если пуста; заменяется только при явном `goalChanged`; LLM не может её очистить. Пользователь может отредактировать/очистить вручную (запись с `source=user`).
- Новое значение существующего ключа — **коррекция** (`correct`, со старым значением в журнале); то же значение — no-op; `null` — снятие ограничения.
- Ограничения — только то, что ответ обязан учитывать (травма, оборудование, диета, исключения); уровень, частота, вес, работа — уточнения. Диета — всегда ключ `diet`, чтобы коррекция заменяла значение.
- Нормализация: регистр, ё/е, диакритика, пунктуация; дубликаты отбрасываются. Лимиты: уточнения 15, ограничения 15, термины 10, открытые вопросы 5, журнал 60, значение 120, цель 200 символов.

### Бюджет контекста
`keepLastTurns` (по умолчанию 4, настраивается в UI/CLI `--keep`) ходов дословно (реплики клипуются, общий предел `maxHistoryChars=6000`), старше — в скользящей сводке (`summaryBatch=2`).
Память — всегда целиком.

## Веб-интерфейс
Вкладка **Chat**, режим «Chat with task memory (Day 25)» (по умолчанию): список сессий / New chat / Reset / Delete, режим памяти (Full / History only / None — для абляции), `keep last N`.
Под каждым ответом: источники, ✓/⚠ цитаты, «ближайшие чанки» для «не знаю», блок «Task memory this turn» (diff памяти, число LLM-вызовов, время), отладочная трасса
(переписанный запрос, retrieved → filtered → reranked). Сворачиваемая панель **Task memory**: цель (редактируется), ограничения (добавить/исправить/удалить),
уточнения, открытые вопросы, история изменений, сброс памяти. Режимы With RAG / Without RAG / Compare остаются одиночными (stateless).
`esc()` теперь принимает не-строки и экранирует кавычки. CLI: `./gradlew :rag:run --args="chat"` (`/memory`, `/goal`, `/reset`, `/new`, `/sessions`, `/quit`).

## Два длинных сценария (`rag/eval/scenarios/*.json`, по 13 реплик)
1. `knee-strength-plan` — 3-дневная силовая программа для новичка с травмой колена без зала; уточнения, дрейф в питание и сон, возврат к плану, follow-up'ы с местоимениями.
2. `fat-loss-vegetarian` — жиросжигание с сохранением мышц: «ем всё» → «на самом деле я вегетарианец» (коррекция), русский фрагмент, вопрос вне корпуса (IDK), возврат к цели.
   *Тема «марафон» из задания заменена*: в корпусе нет материалов про марафон, поэтому вопросы про него были бы честным, но бесполезным «не знаю». Вопросы про сон переформулированы: в корпусе нет норм по часам сна.

Раннер (`scenarios-eval`) пропускает сценарии через настоящий конвейер в трёх вариантах: **FULL** (история + сводка + память), **HISTORY_ONLY** (без памяти), **NONE** (каждое сообщение как отдельный вопрос).
На каждом ходу **кодовые проверки**: источники есть и цитаты верифицированы (или проверенный IDK с уточнением), подделки нет, язык ответа, follow-up разрешён в поисковом запросе,
ответ упоминает/не упоминает ожидаемое, ожидаемый файл-источник, **состояние памяти** (цель, ограничения, уточнения, коррекция залогирована, IDK напоминает цель).
Плюс **LLM-судья** (`GoalJudge`, та же модель, что отвечает → смещение; помечен как LLM-judged) и **ручной вердикт** автора (`rag/eval/scenarios-manual.json`, перечитаны все 26 ответов FULL).
Полный отчёт с таблицей по ходам: `rag/eval/scenarios-report.md` / `.json`.

### Результаты (gemini-3.5-flash, один прогон, 2 сценария, 26 ходов на вариант)

| проверка | FULL | HISTORY_ONLY | NONE |
|---|---|---|---|
| ответ/IDK как ожидалось (код) | 26/26 | 26/26 | 24/26 |
| источники + проверенные цитаты (код) | 25/25 | 25/25 | 23/23 |
| follow-up разрешён в запросе (код) | 18/19 | 18/19 | 15/19 |
| ответ учитывает ограничения (код) | 12/13 | 13/13 | 11/12 |
| ответ избегает исключённого (код) | 3/3 | 3/3 | 1/2 |
| цель в памяти (состояние памяти, код) | 26/26 | – | – |
| ограничения/уточнения/коррекция в памяти (код) | 4/4, 1/1, 1/1 | – | – |
| «цель сохранена» (LLM-судья) | 17/17 | 16/17 | 16/17 |
| «ограничения соблюдены» (LLM-судья) | 15/17 | 14/17 | 12/17 |
| ручной вердикт ok | 22/26 (4 partial) | – | – |
| LLM-вызовов / время LLM на ход | 3.3 / 13.7 с | 2.3 / 10.8 с | 2.0 / 7.9 с |

Что видно: цель не потерялась ни на одном ходу в FULL; коррекция «я вегетарианец» применена (`diet: eats everything…` → `vegetarian`, залогирована как `correct`), ответы после неё про вегетарианские источники;
IDK вне корпуса остаётся проверенным, показывает ближайшие темы и сохраняет цель. Без памяти (NONE) follow-up'ы чаще не разрешаются (15/19), а ограничения хуже соблюдаются по оценке судьи (12/17);
HISTORY_ONLY близок к FULL на этих сценариях — диалоги короткие и вся история помещается в окно, поэтому преимущество памяти (особенно после вытеснения в сводку) здесь **слабо выражено**.

### Честные оговорки и найденные проблемы
- Всего 2 сценария, один прогон, без повторов: различия в 1–3 хода — не статистика. Судья — та же модель (смещение). Кодовые проверки используют списки допустимых слов (нормализация регистра и ё/е).
- Ход 9 сценария 1 («выложи план на три дня»): ответ частично подстраивается под колено, но оставляет lat pulldown и говорит, что Day 3 «нет в тексте» (partial). Ход 5: «those» разрешено только до приседа с гантелью.
  Ход 13 (оба сценария): чек-лист общий, ограничения почти не упомянуты (partial).
- В сценарии 1 FULL ход 5 одна цитата не прошла дословную проверку (⚠ в UI); HISTORY_ONLY сценарий 2 ход 12 — то же. Подделанные источники код не пропустил: фиксируется как предупреждение.
- Первый прогон выявил: таймаут сокета OkHttp (10 с по умолчанию) → таймауты увеличены до 120 с; излишне «охочий» экстрактор (уровень/частота записывались как ограничения, открытые вопросы на каждый вопрос) → промпт ужесточён;
  «устаревшее» уточнение «ест всё» после коррекции → диета теперь всегда ключ `diet`. Эти правки сделаны по результатам прогона на тех же сценариях (подгонка под набор — учитывать при чтении).
- Стоимость: ≈3.3 LLM-вызова (извлечение + переписывание + ответ, иногда ререндер/сводка) и ≈14 с LLM на ход. Объединять экстрактор и переписыватель не стали: переписывание зависит от обновлённой памяти (последовательная зависимость), а выигрыш — один вызов.
- Не проверялось: Android-зеркало (не делалось); параллельные клиенты (сервер обрабатывает запросы последовательно); сводка на очень длинных диалогах (>15 ходов) только юнит-тестами.
- Веб-интерфейс проверен в headless Chrome с живым Gemini (3 хода: память, источники, цитаты, без JS-ошибок; единственная консольная ошибка — 404 ресурса вроде favicon).
