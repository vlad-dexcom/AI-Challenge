# Day 23: реранкинг, фильтрация и переписывание запроса (RAG)

Второй этап после поиска: **пул кандидатов → фильтр по порогу → реранкер → топ-K в промпт**, плюс опциональное
**переписывание вопроса** в поисковый запрос. Всё в модуле `:rag` (чистая JVM), приложение (`Knowledge Coach (RAG)`) получает
выбранные дефолты. Тесты — на фейках, без сети.

## Конвейер

```
вопрос ──(rewrite?)──> поисковый запрос ──> VectorRetriever: topKBefore по косинусу
        ──(filter?)──> ThresholdFilter: cosine >= threshold   (ДО реранкинга; score = косинус)
        ──(rerank?)──> Reranker: переупорядочить + обрезать до topKAfter  (его score ≠ косинус)
        ──> промпт с ОРИГИНАЛЬНЫМ вопросом ──> LLM
```
| Элемент | Что это |
|---|---|
| `RagConfig(topKBefore=10, topKAfter=4, threshold=0.65, filter, rerank, rewrite)` | настройки; `RagConfig.DEFAULT` = фильтр + эвристический реранк, **rewrite выключен**; `RagConfig.PLAIN` = поведение Day 22 (по умолчанию в `RagPipeline(retriever, generator)`, приложение/тесты Day 22 не затронуты) |
| `ChunkFilter` → `ThresholdFilter` | отбрасывает чанки с косинусом ниже порога |
| `Reranker` → `HeuristicReranker` | косинус + доля слов запроса в тексте (0.15) и в заголовке/названии (0.15), затем жадный MMR: штраф 0.3 за схожесть с уже выбранными и за ту же секцию. Веса выбраны заранее и **не подбирались** по eval-набору |
| `Reranker` → `LlmReranker` | отдельный вызов LLM (temperature 0) ставит каждому чанку 0–10; при ошибке/мусоре — порядок по косинусу |
| `QueryRewriter` → `LlmQueryRewriter` | один вызов LLM: самостоятельный, насыщенный ключевыми словами запрос на английском (русский вопрос переводится). Откат на оригинал при ошибке, пустом/многострочном/слишком длинном ответе, «дрейфе» (нет общих слов с англ. вопросом) или если русский вопрос не переведён. `rewrite(question, history = [])` — параметр `history` уже есть для Day 25 |
| `RetrievalTrace` | что дал каждый этап (retrieved / filtered / reranked, поисковый запрос, причина отката) — для отладки, UI и оценок |
| «недостаточно информации» | если фильтр включён и ничего не прошло, LLM **не вызывается**: `RagAnswer.insufficientContext = true`, текст содержит «knowledge base does not cover…». Механизм общий — Day 24 превратит его в обязательный контракт «не знаю» + уточняющий вопрос |

### Эндпоинты LLM
`:rag` `GeminiTextGenerator` ходит в **`generateContent`** (v1beta), приложение — в **Interactions API** (`GeminiApiClient`),
а в `RagAgent` оборачивается в `TextGenerator`. Интерфейс `TextGenerator` остался независимым от эндпоинта:
`generate(system, prompt)` + метод по умолчанию `generate(system, prompt, GenerationOptions(temperature, json))` (реализации,
не знающие про опции, их игнорируют; `GeminiTextGenerator` передаёт `temperature` и `responseMimeType=application/json`) —
задел под structured output Day 24.

## Подбор параметров (sweep, без LLM)
`./gradlew :rag:tools:run --args="sweep"` → `rag/eval/sweep.md`/`sweep.json`: сетка threshold × topK-before × topK-after × rerank
(144 строки) на 30 вопросах `rag/eval/questions.json` (26 из корпуса + 4 вне). Эмбеддинги вопросов кэшируются в `rag/cache/`
(в git не попадает). «Правильный» чанк — из ожидаемого файла (как в Day 21). Precision = доля оставшихся чанков из ожидаемого файла.

**Порог.** Top-1 косинус: вопросы из корпуса (34 = 26 eval + 8 control) — min 0.698, медиана 0.744; вне корпуса: 0.492, 0.500,
0.547, 0.556 (eval), **0.596 (c09 «рекорд в становой»)** и 0.731 (c10 «какой бренд протеина» — тема есть, бренда нет).

| threshold (before=10, after=4) | hit@1 / hit@3 (без реранка) | avg kept | OOC отсечено (4 eval) | вопросов из корпуса отсечено зря |
|---|---|---|---|---|
| 0 | 88.5% / 96.2% | 4.00 | 0% | 0% |
| 0.5 | 88.5% / 96.2% | 3.73 | 50% | 0% |
| 0.55 | 88.5% / 96.2% | 3.50 | 75% | 0% |
| 0.6 | 88.5% / 96.2% | 3.47 | 100% | 0% |
| **0.65** | 88.5% / 96.2% | 3.07 | 100% | 0% |
| 0.7 | 84.6% / 88.5% | 1.67 | 100% | **7.7%** |

Выбрано **0.65**: середина зазора между самым «похожим» вопросом вне корпуса из обоих наборов (c09, 0.596) и самым «слабым»
вопросом из корпуса (0.698). При 0.6 c09 проходит с запасом 0.004 (ловится «по краю»), при 0.7 фильтр уже режет настоящие вопросы.
c10 (0.731) порог не поймает никакой — это тематически близкий вопрос; его отсекает только отказ модели по промпту.

**topK-before.** От 5 до 20 hit@k не меняется (на этом наборе правильный источник и так в топ-5); precision с реранком чуть падает при
росте пула (MMR тянет разнообразные секции): 88.5% (5) → 84.6% (10–20). Выбрано **10** — запас для реранкера (особенно LLM) без
заметной цены; значения 15–20 из плана ничего не дают на этом корпусе.

**topK-after.** 3/4/5: hit@3 одинаков (100% с реранком), hit@5 без реранка 96.2% → 100% только при 5; precision 88.5% / 84.6% / 83.8%.
Оставлено **4** (как в Day 22, сопоставимость; 3 — чуть точнее, но у перефразированных вопросов меньше запас).

## Сравнение режимов (реальный Gemini: `gemini-3.5-flash` + `gemini-embedding-001`, structure-индекс, один прогон)
`./gradlew :rag:tools:run --args="modes-eval --threshold 0.65 --before 10 --after 4"` → `rag/eval/modes-report.{md,json}`
(в json — все ответы и причины вердиктов). Метрики поиска — 26 вопросов из корпуса (hit@k по ожидаемому файлу среди чанков,
попавших в промпт; при topK-after=4 hit@5 = hit@4); ответы — 10 контрольных вопросов Day 22 + 4 вопроса вне корпуса из eval-набора
(6 вне корпуса всего). B/C/… — те же вопросы, разные стадии. Режимы: A без RAG; B обычный RAG top-4 (Day 22); C +фильтр; D +реранк
(эвристика); D2 +реранк (LLM); E +rewrite; F фильтр+реранк+rewrite; G = F с LLM-реранкером.

### Побочный набор: вопросы на русском (корпус английский)
`rag/eval/questions-ru.json` — 16 переводов вопросов из eval (14 из корпуса + 2 вне; перевод мой), отчёт `rag/eval/ru/`.
| режим | hit@1 | hit@3 | MRR | вне корпуса: отказ (включая c09, c10) |
|---|---|---|---|---|
| B обычный RAG | 85.7% | 92.9% | 0.881 | 2/4 |
| C + фильтр | 85.7% | 92.9% | 0.881 | 4/4 (но 1/22 вопросов из корпуса отсечён зря) |
| D + реранк (эвристика) | 85.7% | **85.7%** | 0.857 | 2/4 |
| E + rewrite | 85.7% | 100% | 0.929 | 2/4 |
| F фильтр+реранк+rewrite | **100%** | 100% | 1.000 | 3/4 |

### Что из этого следует (и что — нет)
- **Реранк** — единственный заметный выигрыш по hit@1/MRR на английских вопросах: B 88.5% → D 96.2% (два вопроса из 26, q13 и q16, поднялись на 1-е место; q14, которого в B не было в топ-4, стал 3-м),
  без доп. вызовов LLM. LLM-реранкер даёт MRR 0.981 против 0.974, но стоит +1 вызов (~3 с) — **по умолчанию выключен**.
- **Фильтр** не меняет ни hit@k, ни качество ответов (модель и без него честно отказывалась по правилам промпта: B тоже 6/6), но делает отказ
  детерминированным и **экономит ~36% вызовов LLM** на этой смеси (5 из 14 вопросов отсечены без вызова). c10 (близкая тема) фильтр не ловит —
  отказ дал сам LLM. На русских вопросах порог, откалиброванный на английских, один раз сработал зря (1/22) — косинусы кросс-язычные,
  порог не переносится «как есть».
- **Rewrite** на английских вопросах не помогает (hit@1 88.5% → 84.6%: q22 сместился с 1-го на 2-е место; q14, пропущенный в B, теперь 2-й), зато на русских даёт hit@3 100% и
  решает проблему «чужого языка»; поэтому **выключен по умолчанию**, включается тумблером (и пригодится в Day 25 для follow-up'ов с историей). Русский
  вопрос в UI переписывается в английский запрос, ответ остаётся на языке пользователя.
- Эвристический реранк на русском (лексическое совпадение с английским текстом = 0) не помогает и даже ухудшает hit@3 (92.9% → 85.7%) —
  с rewrite (F) это уходит. LLM-реранкер (D2) на русском лучше эвристики (100% hit@3).
- Качество ответов на 10 контрольных вопросах: с RAG (B–G) 34/34 фактов и 10/10 «correct» у судьи — **потолок набора достигнут уже в B**, отличить режимы B–G по ответам
  этот набор не может. Улучшения видны только в метриках поиска, стоимости и отказах.

### Ограничения (честно)
- **Малый размер:** 26 + 4 вопроса (eval), 10 (control), 16 (RU); один вопрос = 3.8 п.п. hit@k. Разницу B → D (2 вопроса) нельзя считать статистически значимой.
- **Один автор** корпуса, вопросов и перевода; настройки (порог, K) подобраны на тех же 30 вопросах, на которых затем меряем — оптимистичная оценка. Веса эвристики не подбирались, но выбраны мной, зная корпус.
- **LLM-судья** — `gemini-3.5-flash`, та же модель, что отвечает; temperature 0, один промпт (`Judge`), без слепой проверки. Это второе, шумное мнение рядом с подстрочным
  совпадением фактов, не истина. Вручную я перечитал только ответы c04, c09, c10 во всех режимах (с вердиктом судьи согласен), остальные 80 ответов целиком не перечитывал. Для сравнения, мои ручные вердикты Day 22 по тем же 10 вопросам (без RAG: 2✅/5⚠️/3❌; с RAG: 10✅) совпадают с судьёй только в главном: с RAG всё хорошо (10/0/0), без RAG — хуже; но судья без RAG даёт 4/2/4 (строже на одних ответах, мягче на других), так что точные числа для A не надёжны.
- Один прогон при temperature 0.2 (ответы) — недетерминированно; ответы и вердикты сохранены в json. Кэш `rag/cache/` не в git — повторный запуск воспроизводит
  отчёт без сети только на той же машине.
- Задержки зависят от сети/нагрузки API; «кэшированная» задержка = задержка первого вызова.
- Текст «недостаточно информации» от фильтра — на английском независимо от языка вопроса (Day 24 это поправит контрактом ответа).
- Сравнение проведено на `structure`-индексе и одном корпусе из 17 статей.

## Использование
- CLI: `ask "…" --filter on --rerank on|llm --rewrite on --threshold 0.65 --before 10 --after 4` (печатает поисковый запрос и счётчики этапов);
  `sweep`; `modes-eval [--questions … --report …]`. Ключи с флагами требуют значение (`--filter on`).
- Web UI (`ui`, вкладка **Chat**): тумблеры *filter / rerank / LLM reranker / query rewrite*, поля threshold, topK before/after;
  под каждым RAG-ответом раскрывающийся **Pipeline debug**: поисковый запрос (или причина отката rewrite) и таблицы
  retrieved → после фильтра → финальный (rerank score), число вызовов LLM. Всё выключено = Day 22. Если фильтр отсёк всё — жёлтая
  плашка «Nothing passed the relevance filter», модель не вызывалась.
- Приложение: `Knowledge Coach (RAG)` использует `RagConfig.DEFAULT` (фильтр + эвристический реранк, без rewrite и без лишних LLM-вызовов); UI приложения не менялся.
