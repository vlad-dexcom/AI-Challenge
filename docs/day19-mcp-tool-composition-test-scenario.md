# Сценарий проверки композиции MCP-инструментов (Day 19)

Ручной сквозной сценарий для проверки, что пайплайн "Workout Plan Builder" (`find_exercises` →
`build_workout_plan` → `save_workout_plan`) выполняется автоматически одной цепочкой и что данные
корректно передаются от одного инструмента к другому.

---

## Подготовка

1. Убедитесь, что в `local.properties` задан рабочий `GEMINI_API_KEY`.
2. Соберите и установите отладочную сборку:
   ```bash
   ./gradlew :app:installDebug
   ```
3. Откройте приложение — попадаете в обычный экран чата.

---

## Шаг 1 — Выбор персоны

В выборе агента/персоны выберите **«Workout Plan Builder (tool pipeline)»**.

---

## Шаг 2 — Запрос, требующий всей цепочки целиком

Напишите агенту, например:

```
Составь тренировку на ноги на 20 минут для новичка и сохрани её как "Leg Day".
```

**Ожидаемый результат:** за один ответ агент автоматически, без каких-либо дополнительных
сообщений от вас, вызывает все три инструмента по порядку:

1. `find_exercises(goal="legs", level="beginner")` — возвращает сырой JSON-список упражнений.
2. `build_workout_plan(exercises_json=<результат шага 1>, goal="legs", level="beginner",
   minutes=20)` — обрезает список под 20 минут и назначает подходы/повторения.
3. `save_workout_plan(name="Leg Day", plan_json=<результат шага 2>)` — сохраняет план и
   возвращает подтверждение с id.

Откройте экран **MCP** (значок гаечного ключа в верхней панели экрана чата) — в разделе
**«Call log»** должны появиться все 3 вызова подряд, в этом порядке: `connect(...)`,
`listTools() → 3 tool(s): find_exercises, build_workout_plan, save_workout_plan`, а затем три
строки `callTool(find_exercises, ...)` → `callTool(build_workout_plan, ...)` →
`callTool(save_workout_plan, ...)`, каждая с итогом (`ok`/`ERROR`) и началом текста результата.
Если экран MCP пуст — это значит, что используемый шлюз не пишет в `McpCallLog` (баг,
исправленный в этой же итерации для всех трёх MCP-персон: раньше только удалённый
`KotlinSdkMcpGateway` логировал вызовы, а локальные `LocalWorkoutMcpGateway`/
`LocalWorkoutPlannerMcpGateway` — нет).

Финальный текстовый ответ агента должен подтвердить, что план на ноги составлен и сохранён под
именем "Leg Day".

---

## Шаг 3 — Проверка корректности передачи данных между шагами

Это можно проверить двумя способами:

- **По экрану MCP («Call log»)** — аргумент `exercises_json` у `build_workout_plan` должен
  быть тем же JSON-текстом, что вернул `find_exercises` (а не сокращённым/перефразированным
  моделью), а `plan_json` у `save_workout_plan` — тем же текстом, что вернул `build_workout_plan`.
  Каждая строка `callTool(...)` в логе показывает и переданные аргументы, и начало результата —
  их можно сверить визуально прямо на экране, не заглядывая в `adb logcat`.
- **Автоматически** — см. раздел "Автоматические тесты" ниже: `McpToolCallingAgentPipelineTest`
  проверяет это через `assertEquals` на скриптованном сценарии, без сети/модели.

---

## Шаг 4 — Запрос без сохранения (частичная цепочка)

```
Какие упражнения на спину подойдут для среднего уровня?
```

**Ожидаемый результат:** агент вызывает только `find_exercises` (и, возможно,
`build_workout_plan`, если решит сразу предложить план), но **не** `save_workout_plan` — просьбы
сохранить план не было. Это подтверждает, что цепочка управляется намерением пользователя, а не
жёстко зашита как "всегда все 3 шага".

---

## Шаг 5 — Некорректный запрос (неизвестная цель)

```
Составь тренировку на "антигравитацию" и сохрани.
```

**Ожидаемый результат:** `find_exercises` возвращает ошибку "No exercises found for goal ...";
агент сообщает пользователю, что не смог найти подходящие упражнения, и не вызывает
`build_workout_plan`/`save_workout_plan` с пустыми/выдуманными данными.

---

## Шаг 6 — Переживает перезапуск процесса

1. Сохраните план (Шаг 2).
2. Полностью закройте приложение (свайпом из списка задач).
3. Снова откройте его, выберите ту же персону.
4. Спросите: `Какие планы тренировок у меня сохранены?`

**Ожидаемый результат:** ранее сохранённый план всё ещё на диске (`filesDir`), поскольку
`SavedWorkoutPlanStore` — обычный JSON-файл, не зависящий от времени жизни `ChatViewModel`.
(Явного инструмента "прочитать сохранённые планы" в этой цепочке нет — при желании модель может
описать это по памяти диалога/логам вызовов; главная цель шага — подтвердить, что файл на диске
пережил перезапуск, что можно проверить и через `adb shell run-as ... cat
files/saved_workout_plans.json`.)
