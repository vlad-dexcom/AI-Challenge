# Day 22 — Первый RAG-запрос (с RAG / без RAG)

Неделя RAG: Day 21 — индексация, **Day 22 — вопрос → поиск чанков → промпт → LLM, сравнение «с RAG / без RAG»**,
Day 23 — реранкинг/фильтрация по порогу (сегодня не реализуется, но конвейер к этому готов).

## Конвейер

```
вопрос ──(RETRIEVAL_QUERY embedding)──▶ VectorIndex.search(top-k) ──▶ RagPromptBuilder ──▶ LLM ──▶ ответ + источники
                                                    └─ режим NO_RAG: вопрос уходит в LLM как есть, без поиска
```

| Файл (`:rag`) | Роль |
|---|---|
| `Retriever.kt` | `fun interface Retriever` + `VectorRetriever` (эмбеддинг вопроса с `RETRIEVAL_QUERY`, top-k, проверка, что модель эмбеддингов совпадает с `index.meta`). Интерфейс — точка расширения для Day 23: порог/реранкер оборачивают `Retriever`, `RagPipeline` не меняется |
| `RagPrompt.kt` | `RagPromptBuilder`: блок `Context:` с пронумерованными источниками `[n] файл > раздел`, правила (отвечать только по контексту, ссылаться `[n]`, честно сказать «в базе знаний этого нет») |
| `RagPipeline.kt` | `RagMode {NO_RAG, RAG}`, `RagPipeline.ask(question, mode)` и `compare(question)`; результат `RagAnswer` (ответ, использованные чанки, источники) |
| `TextGenerator.kt` | `fun interface TextGenerator` (prompt → text) + `GeminiTextGenerator` (Ktor REST `generateContent`, без SDK, ретраи на 429/5xx). `LlmClient` живёт в `:app`, поэтому `:rag` имеет свой маленький интерфейс, а приложение его адаптирует |
| `ControlSet.kt` | контрольные вопросы: загрузка, валидация против корпуса, автоматическая часть рубрики, markdown-отчёт |
| `Main.kt` | CLI `ask` и `rag-eval` |

Один и тот же системный промпт («опытный тренер») в обоих режимах; режим RAG добавляет правила и контекст
(по умолчанию top-4 чанка стратегии `structure`, ~1.5 КБ каждый). Температура 0.2, модель `gemini-3.5-flash`.

## Агент с двумя режимами (приложение)

`agent/rag/RagAgent.kt` — `Agent` «Knowledge Coach (RAG)» в `AgentCatalog` (`rag-knowledge-coach`).
- Режим `With RAG / Without RAG / Compare` переключается чипами в **Settings** (видны только у этого агента) и
  читается на каждом запросе. В режиме Compare в одном сообщении два раздела: «Without RAG» и «With RAG» + источники.
- Под RAG-ответом выводится список `Sources` (файл > раздел, косинусное сходство).
- Индекс `rag/index/structure.json` (1.5 МБ, эмбеддинги Gemini) копируется в assets задачей Gradle `copyRagIndex`
  (в репозитории остаётся один источник правды); парсится лениво при первом вопросе. Вопрос эмбеддится
  `GeminiEmbeddingClient` из `:rag`, генерация — существующим `GeminiApiClient` через адаптер к `TextGenerator`.
- Не проверялось на устройстве/эмуляторе: сборка (`assembleDebug`) и юнит-тесты проходят, APK содержит `assets/rag/structure.json`.

## CLI

```bash
./gradlew :rag:run --args='ask "How do I fix a deadlift where the bar drifts forward?"'          # оба режима
./gradlew :rag:run --args='ask "..." --mode rag --k 5 --strategy structure'
./gradlew :rag:run --args='rag-eval'     # 10 контрольных вопросов в обоих режимах → rag/eval/control-results.json, control-report.md
./gradlew :rag:test
```
Нужен `GEMINI_API_KEY` (env или `local.properties`, в git не попадает).

## Контрольные вопросы (`rag/eval/control-questions.json`)

10 вопросов: 6 `specific` (ответ — конкретный фрагмент корпуса; «общая» LLM скорее всего ответит иначе),
2 `common` (ответ общеизвестен, LLM справится и без RAG), 2 `out_of_corpus` (в корпусе ответа нет — правильное
поведение: честно сказать об этом). Для каждого: `expectation` в виде `mustContain` (группы альтернатив; ответ должен попасть
в каждую группу) и `expectedSources` (файл + ключевое слово заголовка раздела). `ControlSet.validate` проверяет, что файлы и
заголовки существуют, а ожидаемые факты действительно есть в указанном источнике (тест `ControlSetTest`).

### Выводы
- Где ответ — конкретный фрагмент базы (программы, шаблоны, формулы, числа) RAG дал точные ответы, а модель без RAG
  выдавала правдоподобные, но **другие** версии (c01, c04) — самый заметный выигрыш.
- На общеизвестных темах (c07, c08) разницы по качеству нет: RAG короче и обоснован источниками, без RAG — подробнее.
- Out-of-corpus: без RAG — уверенные (и непроверяемые) утверждения; с RAG — честный отказ. Сходство top-1 для c09 (0.60) ниже,
  чем для вопросов из корпуса (≥0.71), но c10 (0.73) тематически близок к корпусу — один порог это не отловит; это материал для Day 23.

### Ограничения (честно)
- Один прогон, температура 0.2, одна модель — ответы недетерминированы; `control-results.json` содержит ровно те ответы, по которым
  заполнена таблица.
- Автоматические «факты» — подстрочное совпадение групп альтернатив: не понимает смысл (например, перефразированный верный ответ может
  не засчитаться, а упоминание без смысла — засчитаться). Поэтому вердикты ручные и субъективные (один оценщик, не слепой). LLM-судья не использовался.
- «Источник найден» — совпадение файла и заголовка раздела внутри текста любого из top-4 чанков (структурный чанк может объединять
  несколько подразделов, его `section` — первый заголовок).
- Корректность фактов вне корпуса (c09) не проверялась по первоисточникам.
